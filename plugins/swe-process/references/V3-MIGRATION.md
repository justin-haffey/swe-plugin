# V3 compatibility and adoption

Installing V3 and adopting V3 governance are separate operations. Fresh portfolio/solution scaffolds contain V3 procedures and the Luna/medium tester; human approval remains the default until an owner records an applicable policy. Existing files are always skipped by `swe-scaffold`. Adding a tester file does not update an existing agent registry, grant tool access, or change an in-flight Epic's rules.

## Review a migration

V3.1 provides [one adoption preflight](V31-HELPERS.md) combining the proposed diff, package versions, current registry/role/skill, owner compatibility decision and actual-host smoke evidence. Start there for a consolidated readiness report. It is read-only and preserves every migration boundary below.

1. Identify the exact destination, known prior scaffold/package version, current customizations, intended V3 package, and policy boundary. Preserve a recoverable copy or revision of the prior files and record the source version; do not infer a baseline from resemblance.
2. Use a separate, trusted extraction of the known prior scaffold as `Baseline` and the installed V3 scaffold as `Proposed`. Invoke the [read-only diff helper](../scripts/Get-SweMigrationDiff.ps1):

   ```powershell
   & '<swe-process>/scripts/Get-SweMigrationDiff.ps1' -Destination '<repository>' -Baseline '<known-prior-scaffold>' -Proposed '<v3-scaffold>' -AsJson
   ```

   The helper compares paths, object kinds, and SHA-256 bytes for baseline/current/proposed. It returns `Mode: DryRun`, `DestinationWrites: 0`, `PolicyActivated: false`, and exact per-path classifications and hashes. It never applies, deletes, or overwrites files. Without a known baseline, differing existing paths are `BaselineUnknown`. `-IncludeContent` optionally adds exact three-way file text for a review packet; use only in an authorized scope because destination content may be private. The report is a point-in-time proposal, not authority to apply it.
3. Review additions/updates individually. `ProposedUpdate` means current bytes equal the baseline, not that replacement is authorized. Preserve `CustomOnly` and `PreserveCustomization`. Resolve `CustomizationConflict`, `CustomizedRetiredFile`, `BaselineUnknown`, and `TypeCollision` with the owner. Links/reparse points are not followed; no linked destination is implicitly trusted. Files whose requirement retired remain history and are never deleted by the helper.
4. Record adoption in an existing owner-approved ADR/governance decision: scope, effective Epic/revision/assignment, prior/new package versions, changed rules, allowed approval modes, review authority, deferred obligations, and rollback condition. Adopt at the next Epic or new assignment/revision where practical. Explicitly review any in-flight exception, prototype reconciliation, or exhausted review counter; V3 cannot erase them.
5. Apply only the exact separately authorized edits after rechecking current hashes. Merge existing registry entries, local agents, MCP registrations, relative paths, and unrelated settings. `swe-scaffold` remains create-missing only, including under `-force`; rerunning it is not migration. Do not copy portfolio Features or Plans into children.
6. Through `$swe-test`, check the adopted artifact readers, references, TOML/configuration, and actual host role resolution. Confirm `test-runner` resolves to `gpt-5.6-luna` / `medium`, installed `swe-test` resolves, and required runtime/tool permissions support a real scoped smoke run. Static TOML parsing does not prove host routing. Missing capability is Blocked; never silently substitute another model.

## Compatibility matrix

| Source format/version | Target behavior | Reader | Writer | Retained path/ID | Retired future requirement | Rollback condition |
|---|---|---|---|---|---|---|
| V2 accepted Epic/Feature/Plan/Design | Read unchanged; preserve approved criteria and allocations | Process skills and independent validators | Owning skill creates a reviewed successor only for semantic change | Existing artifact IDs, EO/AC IDs, upstream repository/path/revision and accepted history | Repeated upstream narrative in each new artifact | Preserve prior approved revision; no historical rewrite |
| V1 Compact / V2 Detailed architecture | Select Compact for ordinary work; Detailed only for affected concerns needing depth; both honor current contract | `swe-architect` author/review and validators | `swe-architect` at owning level | Existing architecture IDs, parent links, ADRs/contracts and lifecycle | Unconditional Detailed for every artifact; mandatory irrelevant sections | Existing accepted architecture stays usable; review a successor when semantics change |
| V2 Evidence without delivery progress | Derive only verified observations; missing V3 fields remain unknown | `swe-implement`, `swe-validate`, bridge/coordinator | Local `swe-implement` Evidence record; scripts may generate mechanical views | Existing Evidence path and receipt links | Hand-copied progress/continuation prose | Drain deferred checks; reconcile unsupported fields in a reviewed handoff or successor |
| V3 Draft Evidence and deferred checks | Preserve implementation-complete separately from verification and acceptance; drain at checkpoint | Tester, validators, bridge/coordinator | Implementer records observations; validator independently decides | Criterion IDs, failed-attempt receipts, pending obligations, Validation locator | Treating implementation completion as accepted delivery | Complete required early/deferred checks before returning the assignment to V2 gates |
| V2 local/portfolio Validation | Keep distinct decisions and complete relevant coverage | `swe-validate`, `swe-max`, bridge | Independent appropriate validator only | Existing decisions, criterion judgments, evidence and cycle history | Duplicate execution per Feature when one attributable run covers several | Neither package rollback nor migration undoes or invents decisions |
| Legacy bridge `Complete` result | Inspect actual Evidence/Validation before deriving V3 disposition | Internal `swe-bridge` / coordinator | Current bridge writes `ImplementationComplete`, `ValidationPending`, `Validated`, or `Blocked` | Existing destination and artifact/result locators | Full transcript inheritance as mandatory transport; task ID as proof | Legacy reader requires verified completed delivery, not a relabeled pending result |
| Existing customized V2 scaffold/agents/config | Dry-run proposal and explicit scoped adoption; additive install may add missing tester only | `swe-scaffold`, migration helper, destination governance | Authorized migration owner; additive copier only creates absent files | Custom files, agent names/models, registry, MCP/settings and relative paths | Repeated hierarchy manuals in each role; direct developer/UI/validator check execution after adoption | Restore only reviewed governance changes from known prior files; retain new evidence/history |
| V2 named skills and retained artifact templates | Direct specialist commands remain callable; current catalog identifies internal routes | Skill discovery and validators | Each skill's owning package | Supported names/paths and historical links | Duplicate bridge/orchestration authority; unused runtime requirements only when all readers are aligned | Keep prior packages identifiable and restore matching readers/writers together |
| Prototype On/Closing and review-cycle history | Retain scope, journal, deferred entry gates and ordinary reconciliation | `$prototype`, process skills, validators | Authorized run owner and independent reviewers | Existing run IDs, state, evidence, decisions and exhausted counters | No requirement retired can erase a blocker or imply retrospective acceptance | Reconcile/cancel open runs explicitly; rollback is not an Off or Accepted transition |

This matrix retires requirements for future authoring, not accepted documents or supported input formats. No artifact kind is decommissioned in the initial V3 release. Feature/Plan and Concept/Impact may share authoring/review packets but retain separate canonical outputs and decisions; Evidence and Validation remain separate. Historical continuation notes remain evidence; new recovery views derive from canonical records and cannot reset counters or grant approval.

Rollback selects prior package versions and reviews only the governance changes needed to restore compatible operation. It never resets code, deletes receipts, rewrites accepted history, or erases pending obligations. Before resuming an in-flight V3 assignment under V2, finish deferred checks and reconcile progress and approvals through a reviewable handoff. Keep failed attempts attributable throughout.
